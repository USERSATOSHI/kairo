# T6 — Ticket UI

- Status: Accepted
- Date: 2026-07-26

## Problem

Kouro's ticket, run-link, synchronization, and migration records were only
available through package APIs and tests. Operators needed one local surface
that connects planning state to derived execution state without weakening the
ticket/runtime boundary or exposing provider secrets.

## Delivered

- ticket project discovery, ticket-list, ticket-detail, and provider
  configuration HTTP routes;
- API read models that join tickets to derived execution columns, linked runs,
  immutable snapshots, sync state and operations, and migration checkpoints;
- an additive SQLite migration-history projection with ordered stage reads;
- a dashboard-level switch between Tickets and the existing Runs console;
- a horizontally scrollable unified Kanban spanning planning and derived
  execution columns;
- ticket details with priority, labels, assignees, comments, run history,
  snapshot history, synchronization history, and migration history;
- redacted provider configuration cards that never receive or display
  credentials;
- local CLI and standalone API composition of the ticket read stores.

## Design decisions

Ticket joins live in API application use cases, not Elysia handlers or React.
The existing pure board projection remains the authority for columns. Runtime
state is queried through `TicketRunQuery`, so derived execution columns are not
stored on mutable tickets.

Provider configuration is a composition-supplied read model. Browser-based
token entry was rejected because provider credentials and webhook secrets are
server-resolved by design.

## Invariants

- active runs continue to consume immutable ticket snapshots;
- ticket rows contain planning status, never runtime execution status;
- the browser does not derive or persist orchestration decisions;
- migration history records completed durable stages without replacing the
  current migration projection;
- provider credentials are absent from SQLite, API responses, and browser
  state;
- the existing read-only execution graph and approval binding remain
  unchanged.

## Performance impact

Ticket queries are operator-scale. The list endpoint performs bounded
per-ticket run-link queries and runtime lookups; it adds no cache or background
work. History queries use existing ticket indexes and primary-key lookups. The
migration-history table is bounded to four stage rows per ticket.

## Compatibility and migration impact

SQLite initialization adds `ticket_migration_history` with
`CREATE TABLE IF NOT EXISTS`. Existing databases remain readable. Historical
migrations keep their current projection; new stage transitions populate the
ordered history. Existing run, provider, and ticket APIs remain compatible.

## Intentionally deferred

- ticket create/edit/move commands in HTTP or web;
- browser-triggered synchronization and migration commands;
- credential or webhook-secret entry in the browser;
- remote-to-local and remote-to-remote migration.
