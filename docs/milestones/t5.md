# T5 — Ticket migration

- Status: Accepted
- Date: 2026-07-26

## Problem

Local tickets need a safe path to GitHub or Forgejo without losing their stable
Kouro identity. A remote create can succeed immediately before Kouro is
interrupted, so retrying creation without durable recovery would duplicate the
issue. Remote authority also cannot be trusted until the provider returns the
created issue and its normalized content is verified.

## Delivered

- provider-neutral `TicketMigrationService` for GitHub and Forgejo targets;
- durable `prepared`, `remote_created`, `verified`, and `completed` migration
  stages in SQLite;
- an immutable source revision and content snapshot captured before provider
  work begins;
- a stable `kouro-ticket:<ticket-id>` marker embedded in remote issue content;
- marker lookup before every create to recover the remote identity after an
  interrupted create;
- remote read-back verification of provider identity, title, description,
  open/closed state, labels, and assignees;
- optimistic local revision validation before the authority switch;
- atomic replacement of the local binding with the verified remote binding;
- durable typed failures that preserve the last safe migration stage;
- restart coverage for interruption after the remote side effect but before
  its local checkpoint.

## Design decisions

Migration is an application service in the ticket bounded domain. It uses the
existing provider contract for remote effects, a migration-store port for
durability, and a narrow binding-writer port for the final authority switch.
The deterministic runtime and immutable run snapshots are not involved.

The remote marker is used instead of assuming provider create requests are
idempotent. Reconciliation-by-title was rejected because titles are mutable and
not unique. Switching authority immediately from the create response was also
rejected because it would accept an unverified or normalized-away response.

## Invariants

- only a locally authoritative ticket can start migration;
- a ticket has one migration target and captured source revision;
- local edits after preparation block the authority switch;
- remote creation is preceded by marker lookup;
- multiple matching markers are a typed verification failure;
- authority remains local until provider read-back matches the captured
  snapshot;
- an interrupted migration resumes from its last durable stage;
- completed migration retries return the existing binding without another
  provider create;
- credentials and secrets are absent from migration state;
- active and historical run snapshots remain unchanged.

## Performance impact

Migration is an operator-scale path, not a runtime hot path. Each migration
performs one provider list for duplicate recovery, at most one create, one
read-back, and a bounded number of SQLite writes. No cache or unbounded retry
loop was introduced.

## Compatibility and migration impact

SQLite initialization adds the `ticket_migrations` table with
`CREATE TABLE IF NOT EXISTS`; existing ticket databases remain readable.
Provider credentials remain constructor-only inputs. Existing local, GitHub,
Forgejo, synchronization, and run-snapshot behavior is unchanged.

## Intentionally deferred

- migration HTTP, CLI, and web controls;
- migration-history UI and provider configuration, which remain T6;
- copying local comments and relationships, which do not yet have a
  provider-neutral duplicate-safe migration contract;
- remote-to-local and remote-to-remote authority transfer.
